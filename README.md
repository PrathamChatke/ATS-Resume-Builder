# ATS Resume Screener

A resume screening tool for recruiters: upload a candidate's resume (PDF or DOCX), optionally
match it against a job posting, and get back a deterministic ATS score plus professional,
MAANG-style improvement suggestions generated by Google Gemini.

## How it works

1. A deterministic, rule-based engine (`backend/.../scoring`) parses the resume and computes a
   0-100 ATS score from five weighted categories: keyword match, formatting, section structure,
   impact/quantification, and contact info. This part is fully explainable and reproducible —
   no AI involved.
2. Those findings are handed to Gemini, which only phrases them into specific, professional
   suggestions — it never invents facts or changes the score.
3. Upload returns immediately (`202 Accepted`); parsing, scoring and suggestion generation run on
   a background thread pool so the API stays responsive under load. The UI polls the resume until
   it's `PROCESSED`.

## Prerequisites

- Java 17
- Node.js 18+
- A Postgres database — either local/Docker, or a free hosted one like
  [Supabase](https://supabase.com) (no Docker needed for the database in that case)
- A Google AI Studio API key: https://aistudio.google.com/apikey

## Running locally

First, set up your secrets once:

```bash
cp .env.example .env
```

Then open `.env` and fill in `JWT_SECRET` and `GOOGLE_API_KEY`. If you're using a hosted Postgres
(e.g. Supabase) instead of local/Docker Postgres, also fill in `SPRING_DATASOURCE_URL`,
`DB_USERNAME`, and `DB_PASSWORD` from your provider's connection details (see the comments in
`.env.example`). `.env` is gitignored — it never gets committed.

### 1. Start Postgres (skip this if you filled in a hosted Postgres above)

```bash
docker compose up postgres -d
```

### 2. Run the backend

Load the `.env` values into your shell session, then run the app:

```bash
cd backend
export $(grep -v '^#' ../.env | xargs)
./mvnw spring-boot:run
```

(PowerShell equivalent: `Get-Content ..\.env | Where-Object {$_ -match '=' -and $_ -notmatch '^#'} | ForEach-Object { $k,$v = $_ -split '=',2; [Environment]::SetEnvironmentVariable($k,$v) }` then `.\mvnw spring-boot:run`.)

The API comes up on `http://localhost:8080`. Flyway applies the schema automatically on startup —
against Supabase this just means your tables show up there too.

### 3. Run the frontend (dev mode, hot reload)

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. It proxies `/api` calls to the backend on port 8080.

### First account

The first account registered becomes an `ADMIN`; every account after that is a `RECRUITER`.
There's no separate sign-up flow to lock down for a first release — just register once from the
login screen.

## Building a single production artifact

The frontend build output is copied straight into the Spring Boot jar's static resources, so the
whole app ships as one deployable artifact:

```bash
cd frontend && npm run build   # outputs into backend/src/main/resources/static
cd ../backend && ./mvnw clean package
java -jar target/*.jar
```

## Running everything with Docker Compose

```bash
JWT_SECRET="a-random-secret-at-least-32-characters-long" \
GOOGLE_API_KEY="your-google-ai-studio-key" \
docker compose up --build
```

This builds the frontend into the backend jar as part of the Docker image, and brings up
Postgres + the app together.

## Secrets

`JWT_SECRET` and `GOOGLE_API_KEY` are never written into any file that gets committed. They're
read from environment variables at runtime (`application.yml` only references
`${GOOGLE_API_KEY:}` as a placeholder, not the real value).

For local/dev use, copy `.env.example` to `.env` in the repo root and fill in real values:

```bash
cp .env.example .env
```

`.env` is already listed in `.gitignore`, so it can never be accidentally committed.
`docker compose` reads it automatically. If you run the backend directly with `./mvnw
spring-boot:run` instead of Docker, export the same two variables in your shell first (see below)
— Spring Boot does not read `.env` files on its own outside of Compose.

For an actual production deployment, put these in whatever secrets manager your host provides
(e.g. a cloud provider's secret store or a CI/CD secret) rather than a `.env` file on disk.

## Configuration

All configuration lives in `backend/src/main/resources/application.yml` and is overridable via
environment variables:

| Variable | Purpose |
|---|---|
| `DB_USERNAME` / `DB_PASSWORD` | Postgres credentials |
| `SPRING_DATASOURCE_URL` | Postgres JDBC URL |
| `JWT_SECRET` | HS256 signing secret, 32+ characters. **Must** be overridden outside local dev. |
| `GOOGLE_API_KEY` | Google AI Studio API key for Gemini-generated suggestions |
| `GEMINI_MODEL` | Defaults to `gemini-2.5-pro` |
| `STORAGE_ROOT` | Local directory resumes are stored in |

Scoring category weights are under `app.scoring.weights` in `application.yml` if they need tuning
for a specific hiring pipeline.

## Tests

```bash
cd backend
./mvnw test
```

The scoring engine has plain unit tests (no Docker required). The `AuthControllerTest` and the
application context test use Testcontainers to spin up a real Postgres instance, so Docker must
be running for those.
